# Emission Calculator — portfolio demo

> **Что это.** Демо‑пример расчётной системы для лаборатории промышленных выбросов: от заполнения акта отбора проб на планшете — до готового протокола испытаний с расширенной неопределённостью при P = 0,95.
>
> Все данные, названия заказчика, номера приборов и подписи — **вымышленные**. Реальные клиентские файлы остались внутри лаборатории; здесь — инженерный слепок логики.

## Зачем это показано

Работа в аккредитованной лаборатории атмосферных выбросов я поддерживал расчётный «движок» в Excel, который реализовывал методики ГОСТ 33007‑2014, ГОСТ 17.2.4.06‑90 / 17.2.4.07‑90 и РМГ 62‑2003. Через систему прошло ~820 проб / 82 заказчика / 0 формульных ошибок; расчёт одного протокола с ручного 40‑минутного пересчёта сократился до 4 минут.

Этот репозиторий — обезличенная миниатюрная версия той системы. Он нужен не для работы лаборатории, а чтобы **публично показать инженерный подход**: как превращать плотные метрологические требования в прослеживаемый, проверяемый, пересчитываемый артефакт.

## `calculator.xlsx` — как читать

Файл построен как мини‑ETL внутри Excel: входы отдельно, коэффициенты отдельно, расчёты отдельно, выход отдельно. Каждый лист — отдельный слой.

| Лист | Роль | Цветовой код |
| --- | --- | --- |
| `СИ_Справочник` | таблицы калибровок средств измерений (K_тр, δ%) | 🟢 зелёный — неизменяемые константы |
| `Данные_отбора` | значения из акта отбора (P_д, t_г, Δm, τ …) | 🟡 жёлтый — вводится вручную |
| `Расчёт` | основная рабочая таблица, все формулы | 🟠 оранжевый — вычисляемые |
| `Итог_в_протокол` | таблица результатов, готовая к копированию в протокол | 🟢 ярко‑зелёный — итог |

### Ключевые формулы (лист `Расчёт`)

```
ρ_р    = 1.293 · (Б·133.3 + P_ст)/101325 · 273/(273+t_г)    (плотность газа при р.у.)
W      = K_тр · √(2·P_д / ρ_р)                              (скорость потока, ГОСТ 17.2.4.06)
Q_р    = S · W                                              (объёмный расход при р.у.)
Q_нy   = Q_р · 273 · (Б·133.3+P_ст) / (760·133.3·(273+t_г)) (расход при н.у.)
V_ну   = W_р · τ · (P_р·1000+Б·133.3) · 273 / ((273+t_р)·760·133.3)
Z      = Δm · 10⁶ / V_ну                                     (запылённость при н.у.)
Ф      = Z · Q_нy / 1000                                     (массовый выброс)

ΔX / X = 2 · √( Σ (δ_i / 2)² )    при P = 0,95, k = 2        (РМГ 62-2003)
```

Все формулы — живые; измените любую ячейку на листе `Данные_отбора`, и итоговая таблица на листе `Итог_в_протокол` пересчитается сама.

### Проверка непротиворечивости

Для исходных данных демо `Расчёт → B26 (Запылённость)` даёт ровно **35,5 мг/м³** — то же значение, что получалось в оригинальной лабораторной системе для аналогичного источника. Это подтверждает, что обезличенная версия воспроизводит исходную метрологическую логику, а не просто «выглядит похожей».

## `sampling_act.xlsx` — почему Excel, а не docx

В поле пробоотборщик работает с планшета. Docx на 12″ экране неудобен; крупноблочный xlsx с выпадающими списками и жёлтой «подсветкой ввода» — удобен. Лист построен так, чтобы:

- крупные ячейки, плотности экрана планшета достаточно;
- каждое значение в отдельной ячейке (а не в абзаце) — чтобы autosync с расчётным файлом шёл по координатам, без распознавания текста;
- формула площади сечения `S = π·D²/4` вычисляется прямо в акте, пробоотборщик проверяет адекватность геометрии ещё на объекте;
- подписи — как поля для tablet signature.

## `protocol.docx` — формат выдачи

Генерируется скриптом на `docx-js` (Node). Макет по образцу реального протокола: шапка лаборатории → шапка протокола → таблица результатов (7 показателей потока + 5 концентраций газов) → таблица средств измерений → раздел «Мнения и интерпретация» → подписи.

Результаты в таблице — те же числа, что считает `calculator.xlsx`.

## Как это связано с Python‑бэкграундом

В лабораторной версии я упирался в два ограничения Excel:

1. **Нет прослеживаемости** между актом отбора и протоколом — если заказчик через год спросит, откуда взялось число, приходится открывать 3 файла.
2. **Нет валидации** — ошибка в ячейке живёт до первой ручной проверки.

Решение поэтапное:
- здесь, в демо — цветовая кодировка + явное разделение на листы как дисциплина;
- в продакшен‑версии, над которой я сейчас работаю — миграция на FastAPI + SQLAlchemy + PostgreSQL, где акт отбора и протокол становятся строками в БД с ссылкой `protocol.sampling_act_id`, а формулы переписаны как проверяемые Python‑функции с pytest.

См. репозиторий [life-tracking-bot-python-public](https://github.com/proggdd/life-tracking-bot-python-public) — там же применён тот же подход: перенос рабочей Apps Script системы в Python со строгой схемой и Alembic‑миграциями.
